# 核心完善 P3 报告

> 2026-09-24，由 Claude 执行。本报告只写统计和测试任务里的简短问答，不含真实对话、图片和本机路径。设计见 [plan.md](plan.md) 第 11 节，任务见 [tasks.md](tasks.md)。测试调用模型一律用 gpt-6-sol、推理强度 low。

## 1. 结论

核心已经可以按“装好即用”的方式运行，界面之外的部分都已完成并通过自测：

- **引擎（本地代理）**：全机只运行一个，由插件服务自动拉起，崩溃后自动恢复，随 Codex 退出。
- **插件服务**：由 Codex 启动，负责拉起引擎、充当看门狗，并给面板提供数据。
- **一键安装和恢复**：`cam.ts install` / `uninstall` / `status`。
- **面板数据**：图片列表、缩略图、勾选和取消（只允许用户操作）、上次请求统计、模型索要的编号。

还没做的：用户可以手动打开的界面（P4），以及把核心装进用户自己的桌面版、实际用一轮（需要用户配合）。

## 2. 试验面板（P3-1）

在用户的桌面版上：

- 面板出现在 Codex 右侧的侧栏里，带标签页；页面显示、和桌面版握手、回调插件服务、data URL 小图都正常。
- 页面访问 `localhost` 被 CSP 拦截，和上游 #45913 一致，所以面板只能经插件服务拿数据。
- 面板回调时，桌面版会带上当前任务的编号。
- 插件服务的工具不会直接列给模型，要靠模型搜索；gpt-6-sol 第一次没找到，点名之后才打开。每次打开还要花一轮请求。所以界面要由用户自己打开（用户已确认）。

## 3. 稳定性自测（P3-5）

用我们自己启动的 Codex，环境和桌面版一致，配置与安装后相同，但通过命令行参数传入，不改用户的 `config.toml`。7 项检查全部通过：

| 场景 | 结果 |
|---|---|
| 插件服务拉起引擎 | 建好任务后 0.8 秒，引擎就起来了；其他实例发现它在运行，不会重复启动 |
| 两个任务同时用 | 只有取消了图的任务一被改写；任务二一直原样转发（走 WebSocket，没有收到 426） |
| 引擎崩溃 | 被杀后 1.6 秒由插件服务拉起，之后的对话正常 |
| 压缩历史 | 压缩请求同样被改写；压缩后再问被取消的图，模型回答“需要 IMG-001。当前没有提供 a.png 的画面，我无法判断颜色和形状。” |
| 全部 7 轮对话 | 都完成，没有报错和重试 |

## 4. 引擎的生命周期（实验）

- Codex 会把插件服务和插件服务拉起的进程放在一起管理：拉起引擎的那个插件服务一结束，引擎也跟着结束；Codex 退出时，引擎同样随之结束。所以“随 Codex 退出”是自动实现的。
- 代价是：如果拉起引擎的那个插件服务实例先被 Codex 结束（多见于 Codex 刚启动的几秒），引擎会断开最多 3 秒，然后由其他实例重新拉起（实验里 2.5 秒内完成）。
- 由 `cam.ts install` 在终端里拉起的引擎不受这个影响，它靠自己检查 Codex 进程，Codex 全部退出 30 秒后自行退出。
- 如果以后这种断开真的碍事，可以让引擎彻底脱离 Codex 的管理，例如用 Windows 计划任务来启动它。不过这需要在用户的系统里注册一个任务，届时再请用户决定。

## 5. 分叉任务的勾选

- 自测发现：分叉出来的任务原本从“全部勾选”开始，所以父任务里取消的图，到了分叉任务里又会照常发送。
- 用户决定分叉时沿用父任务的勾选。
- 现在的做法：分叉任务第一次用到时，如果还没有自己的勾选，就复制父任务在分叉之前取消的那些，存成自己的；之后两边各管各的。分叉的分叉会逐层向上找。
- 父任务的编号和分叉时间，取自分叉任务本地记录的第一行（`forked_from_id`、`timestamp`）。4 个单元测试覆盖。

## 6. 装进桌面版实测（P3-6）

用 `cam.ts install` 写入全部配置（代理地址、`respect_system_proxy`、插件服务，以及 `.env` 的 `NO_PROXY`，因为用户的环境变量里有代理），然后由用户重启 Codex：

| 步骤 | 结果 |
|---|---|
| 关闭 Codex | 安装时启动的引擎在 Codex 进程全部退出后自己退出（日志原因：“no Codex process left”） |
| 重新打开 Codex | 插件服务由 Codex 自动启动并拉起引擎。头 40 秒里，几个短命的插件服务实例先后拉起引擎又随之结束，引擎来回重启了 4 次；有一次两个实例同时去拉起，后到的那个发现端口已被占用，自行退出了。之后稳定下来 |
| 上传两张图，只回复“收到” | 经过引擎，走 WebSocket |
| 用命令行取消 a.png（IMG-002） | 引擎关掉这个对话空闲的连接 |
| 问 a.png 的颜色和形状 | 握手收到 426，改走 HTTP；请求被改写，IMG-002 换成普通占位符，只发出 1 张图；模型回复“需要 IMG-002” |
| 关闭 Codex | 没有 Codex 进程残留，引擎随之结束 |
