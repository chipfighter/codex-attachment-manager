# 技术方案

> 目标、约束和验收关卡以 [spec.md](spec.md) 为准。本文件说明怎么做、为什么这样做。第 1–8 节是阶段 0 的设计（已完成，结果见 [phase0-report.md](phase0-report.md)）；第 9、10 节是代理路线的接入（P1）和按勾选改写（P2），都已在桌面版验证通过；第 11 节是正在做的面板（P3）。

## 1. 已知事实（2026-09-24）

### 验证环境（Windows）

- Codex 桌面版：`OpenAI.Codex` 26.917.6896.0（MSIX）。它自带的 CLI 位于 `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe`，版本是 `codex-cli 0.155.0-alpha.16`。`<hash>` 会随桌面版更新而变化。
- 验证机上没有运行中的 app-server 后台服务（执行 `codex app-server daemon version` 连接失败），所以桌面版目前不经过这个服务。
- `~/.codex` 里和本项目有关的位置：
  - 会话记录：`sessions/**/*.jsonl`
  - 线程历史库：`thread_history_*.sqlite`；另有 `state_*.sqlite`
  - 生成的图片：`generated_images/`
  - 附件：`attachments/`（验证机上目前只有文本附件）
  - 线程写锁：`thread-writer-locks/`
- 样本任务的内联图片在 `sessions` 的 JSONL 记录里，该任务没有对应的 `generated_images/<thread-id>` 目录。它生成的 PNG 原件散落在用户项目文件夹的多个子目录里；具体位置执行者已知，不写进仓库。所以索引器不能只扫一个目录。
- 样本 fork 在“只发文字”之后调用了看图工具，把 4 张图以内联形式写进了历史，单条结果约 13.3 MB。（此条和上一条由 Codex 在验证机上核实。）

### 上游 Codex（公开源码和 PR）

- 历史图片目前以内联 base64 的形式保存，每一轮都整包重新发送。0.156.0 已合入 `file_id` 引用和附件存储（[#45794](https://github.com/openai/codex/pull/45794)、[#46065](https://github.com/openai/codex/pull/46065)），但 main 分支的 app-server 仍在用内联存储，而且已有的图片不会被迁移。
- [#45794](https://github.com/openai/codex/pull/45794) 会拒绝“最近图片里含文件引用”的改图请求，所以改图这条路必须实测。
- `thread/inject_items` 向线程追加原始 Responses 条目：条目进入模型可见的历史，但不产生新的用户轮次（见 [app-server 文档](https://developers.openai.com/codex/app-server)）。
- `postToolUse` hook 只能替换 MCP 工具的输出，改不了内置的 `view_image` 和生图。
- `codex app-server` 的相关能力：
  - 用 `-c key=value` 覆盖配置；
  - 用 `--enable` / `--disable` 开关功能，例如 `view_image`；
  - 用 `generate-ts` 生成和本机版本一致的 TypeScript 类型。
- 按公开源码，模型发起的 MCP 调用会附带线程和会话标识（[mcp_tool_call.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/mcp_tool_call.rs)）。本地 stdio 服务实际收到什么，还没有实测。

## 2. 两条路线

### 路线 A：重建（首选，待验证）

1. 只读读取原任务的历史，建立素材索引。
2. 通过 app-server 新建任务，依次调用：
   - `thread/start`
   - `thread/inject_items`，注入按第 3 节规则搬过来的历史
   - `thread/name/set`
   - `turn/start`，附上选中的图
3. 之后用户在桌面版里继续这个新任务。

### 路线 B：交接包（回退方案）

生成一份文字摘要，加一个装有选中图片的文件夹。用户手动开新任务，贴入摘要并附上图片。实现成本低，但连续性差。

### 怎么选

> 阶段 0 结果：关卡 1–6 全部通过，路线 A 在技术上可行。但用户不接受“重建后在界面上看不到原对话”，所以没有采用，改为验证代理路线（第 9 节）。以下是阶段 0 当时的规则。

- spec 阶段 0 的关卡 1–6 全部通过：路线 A 作为首版主方案。
- 关卡 2 或 3 失败：首版改用路线 B，路线 A 留作研究。
- 关卡 4 或 5 失败：先当实现问题排查。如果确认是结构性原因（例如 app-server 会自动带回未选的图片），改用路线 B。
- 关卡 6 失败：调整占位符的措辞。这不影响路线选择，但首版发布前必须通过。

## 3. 路线 A 的搬迁规则

- **搬过去的内容**
  - 用户消息的文字；
  - 助手的 `message` 回复；
  - 占位符和重复引用，格式见 spec 的“占位符”一节。
- **不搬的内容**
  - reasoning 条目：它们是加密的，不能保证在另一个线程里可用；
  - 压缩标记；
  - 原始的工具调用及其输出。每次工具调用改写成一行说明，例如“（此处 image_gen 生成了 IMG-005，提示词：……）”。
- **图片放在哪**
  - 注入的历史里只放占位符，不放图片。选中的图片作为下一轮 `turn/start` 的附件发送，并在该轮文字里写明“附件 1 = IMG-004”。
  - 这样“勾选”和“重新勾选”走的是同一条路：都在下一轮作为附件发送，不需要重建。这种方式也最接近改图工具取“最近图片”的方式。
- **磁盘上找不到原件的图片**（只存在于记录里）：解码后缓存到本地工作目录，作为附件的来源。缓存只是副本，不写回任何原始位置。
- **原任务做过压缩时**：记录压缩条目的形态（是否可读），并在报告里说明搬的是哪一段历史。
- **条目格式**：以 `generate-ts` 在本机生成的协议类型为准。

## 4. 防止图片再次堆积

在新任务里，模型自己调用 `view_image` 之类的工具时，仍会把图片以内联形式写回历史，样本 fork 就是这么变大的。

阶段 0 做一个附加实验：用 `--disable view_image`，或在 `thread/start` 里用配置覆盖，关掉看图工具，记录这样是否可行、对流程有什么影响。首版方案按实验结果再定。

## 5. 测量方法

- **请求字节数**：调高我们自己启动的 app-server 的日志级别，从日志里读出请求体大小。上游的日志里出现过 `pre_compression_bytes=... post_compression_bytes=...` 这类记录，具体用哪个日志开关由执行者查证。
- **历史构成**：只读检查新任务的记录，统计内联图片的数量和字节数，确认里面没有未选的图片。
- **原始文件不变**：操作前后分别计算样本记录文件和相关素材文件的哈希，然后对比。
- **估算值**：注入文字的字节数，加上选中图片转成 base64 后的字节数，与实测的请求字节数对比。

## 6. 安全措施

- **用同一个 codex**：独立的 app-server 用桌面版自带的那个 `codex.exe` 启动，避免状态库迁移不一致。如果版本对不上，先停下报告。
- **先备份**：第一次通过 app-server 创建任务前，用 SQLite 在线备份（只读打开源库）给 `state_*.sqlite` 和 `thread_history_*.sqlite` 生成一致的副本，放进本地工作目录 `local/`（已被 git 忽略）。
- **测试任务加前缀**：测试用的新任务，名称统一加前缀 `[CAM测试]`，方便用户识别和归档。
- **先释放写锁**：在桌面版里打开新任务之前，先结束我们的 app-server 进程，释放线程写锁。
- **不改用户配置**：不修改用户的 `config.toml`。需要的配置用命令行的 `-c`、`--disable`，或 `thread/start` 里的配置覆盖。
- **不碰认证信息**：不输出、不记录认证信息（例如 `auth.json` 的内容）。
- **沙箱权限**：独立的 app-server 需要联网和写入 `~/.codex`，可能被 Codex 沙箱拦下。遇到这种情况，请用户批准提权，或者由用户在普通终端里运行。

## 7. 关键决策

| 决策 | 原因 |
|---|---|
| 不改原生任务，改为在新任务中继续 | 官方没有删除历史条目的接口；直接改记录文件不安全 |
| 路线 A 优先于只交接摘要 | 保留完整的对话文字，连续性更好 |
| 只搬文字和占位符，不搬 reasoning 和工具记录 | 加密条目和调用配对不可靠，工具记录还可能夹带大块内容 |
| 选中的图作为下一轮的附件发送 | 一套机制同时覆盖勾选和重新勾选，也贴近改图工具的取图方式 |
| 改为验证代理路线 | 用户要求在同一个任务里勾选、取消文件时对话连续可见，重建路线做不到 |
| 面板优先放进 Codex 对话（MCP Apps），做不到再做跟随窗口的外置面板 | 用户 2026-09-24 决定；对话内卡片在 Windows 上仍有渲染问题，需要先验证 |
| 新图默认勾选，包括内容相同的副本 | 用户 2026-09-24 决定：装了工具但不取消任何图时，表现和没装一样 |
| 每条出现记录单独编号、单独勾选，内容相同的另外标出 | 用户要能只取消副本、保留原图；模型说“需要 IMG-007”时只对应一条 |
| 编号只由本地记录决定，命令行（以后是面板）和代理各自计算 | 两边不用共享状态，编号也不会对不上 |
| 取消了图的任务改走 HTTP | WebSocket 只发新增条目，已发的图留在服务端；426 是 Codex 自己的回退路径 |
| 改写不了就原样发送，并记下原因 | 宁可多发，也不让对话中断；面板要把这种情况显示出来 |
| 代理跟着 Codex 一起启动、一起退出 | 用户 2026-09-24 确认；配置指向代理而代理不在时，Codex 连不上。做法待验证，候选是让 Codex 自己启动的插件本地服务顺带运行代理 |
| 首版只做单个任务、只做图片 | 全量扫描很重；图片是当前的痛点 |
| 用 TypeScript/Node | 验证机已有 Node 24；能生成官方协议类型；面板也用同一种语言 |

## 9. 代理路线（验证中）

### 思路

在 Codex 和 OpenAI 之间放一个只在本机监听的代理。

1. Codex 照常把完整请求发给代理；
2. 代理按这个任务当前的勾选，把没选的图换成占位符，再转发出去；
3. 回复原路返回，由 Codex 照常记进同一个任务。

任务不换，历史和界面都不动，勾选和取消从下一次请求起生效。

### 接入方式（已查证）

- **地址覆盖**：`config.toml` 顶层的 `openai_base_url` 可以覆盖内置 openai 通道的地址，ChatGPT 登录模式下同样生效。改了地址后，任务的归属仍然是 openai。
- **路径后缀**：地址必须以 `/backend-api/codex` 结尾，否则 Codex 会关掉后端专用的接口。所以代理地址用 `http://localhost:<端口>/backend-api/codex`（为什么不用 `127.0.0.1`，见下文），代理再把同样的路径转发到 `https://chatgpt.com`。
- **经过的接口**：对话走 `…/responses`，默认用 WebSocket，失败时回退到 HTTP；生图、改图走同一个通道的 `…/images/generations` 和 `…/images/edits`。
- **认出任务**：每个请求的请求头里都有 `x-codex-turn-metadata`（其中有 thread_id、turn_id），请求体里还有 `prompt_cache_key`，代理据此认出请求属于哪个任务。
- **系统代理**：我们的代理往外连 chatgpt.com 时，自动沿用系统代理设置（环境变量或 Windows 设置），不需要用户填写。
- **Codex 连本地代理（P1 实测）**：
  - Codex 默认按环境变量选择代理。用户环境里有 `HTTP(S)_PROXY`、没有 `NO_PROXY` 时，连本地地址的请求也会被交给系统代理，然后失败。
  - 所以要同时打开 `features.respect_system_proxy`，让 Codex 先看 Windows 的代理设置，并把地址写成 `localhost`：Windows 设置里的 `<local>` 只让不带点的主机名直连。
  - 生图和改图要等 Codex 包含 #47742 的版本才会遵守这个开关。上游从 `0.158.0-alpha.8` 起包含；桌面版 26.917（自带 `0.155.0-alpha.16.4`）还没有，而且检查更新显示已是最新。在此之前，环境变量里有代理、又没有 `NO_PROXY` 的用户，开着代理时不能生图和改图。详见 [p1-report.md](p1-report.md)。
- **不等更新的办法（用户 2026-09-24 同意；P2-6 在桌面版验证通过）**：
  - Codex 每次启动都会读 `$CODEX_HOME/.env`，把里面的变量设进自己的进程（`CODEX_` 开头的除外，见源码 `arg0` 的 `load_dotenv`）。
  - 生图模块用的默认客户端认 `NO_PROXY`（P1-3 已实测）。所以在 `.env` 里写 `NO_PROXY=localhost,127.0.0.1,::1`，生图和改图不等 #47742 也能连到本地代理。
  - 用户自己设过的 `NO_PROXY` 条目会合并进来，因为 `.env` 里的值会在 Codex 进程里替换掉原来的值。`.env` 里已经有用户自己的 `NO_PROXY` 时，不覆盖，直接报告。
  - 仍然保留 `respect_system_proxy`：读取 `.env` 这一行为没有写进官方文档，保留它，对话能不能连上就不依赖 `.env`。万一以后的版本不再读 `.env`，最坏的结果也只是生图和改图暂时连不上；而那些版本本来就已经包含 #47742。
  - 影响范围只有 Codex 自己的进程和它启动的工具，而且只涉及本机地址。留下这一段也无害：它只让本机请求直连，不会像 `openai_base_url` 那样在代理不在时让 Codex 连不上。
  - 产品里只在需要时写入：桌面版的 Codex 还没有 #47742，而且用户的代理设置会拦住发往本机的请求。Codex 更新后自动删掉。
- **元数据差异**：地址不是官方域名时，Codex 会去掉请求里附带的原始工具结果元数据（`executed_tool_calls` 里的 `tool_result_metadata`）。这是随请求上报的内部元数据，不是模型看到的内容。

### P1：只转发、不改写

- **转发**：原样转发 HTTP 请求和 WebSocket 连接，不改动任何字节，结果按流式返回。
- **日志**：只记元数据，包括方法、路径、状态码、字节数、耗时、任务 ID，以及请求里的图片数量和字节数。不记认证信息，也不记对话内容。
- **配置**：
  - 工具管理两段带标记的设置：顶层的 `openai_base_url`，以及 `[features]` 里的 `respect_system_proxy`（没有这张表时，改为顶层的 `features.respect_system_proxy`）；
  - 改之前把原文件备份到 `local/`；
  - 恢复时只删掉带标记的段落。桌面版运行时自己也会写 `config.toml`，所以绝不能用旧备份整体覆盖；
  - 用户自己设过 `openai_base_url`，或者把 `respect_system_proxy` 设成了 false，一律不覆盖，直接报告。
- **验证顺序**：
  1. 先用我们自己启动的 app-server 走一遍：文字、附图、生图、改图。这一步用 `-c openai_base_url=…` 指定地址，不改配置。
  2. 再改桌面版的配置。用户重启桌面版后，在任务里依次发文字、上传图片、让它生图、让它改图。
  3. 看代理日志，确认这些请求都经过了代理并且成功，不同任务的请求各自带着自己的任务 ID。
- **风险**：代理没在运行时，Codex 会连不上。验证期间代理一直开着；验证结束后恢复配置，或者由用户决定是否保留。

P1 通过后，再按用户的节奏一步步探索改写。

## 10. 按勾选改写（P2）

### 已查证的 Codex 行为

依据桌面版自带的 `0.155.0-alpha.16.4` 的源码，以及 P2-1 的抓包：

- **WebSocket 和 HTTP**：
  - WebSocket 连接上，Codex 只发新增的条目，靠 `previous_response_id` 接上服务端保存的历史。代理没法在这条连接上去掉已经发过的图。
  - HTTP 每次都发完整历史。
  - WebSocket 握手收到 426 时，Codex 立即改走 HTTP，并在这个会话里一直走 HTTP，不报错、不重试。
  - 缓存的 WebSocket 连接被关掉后，下一次请求会重新握手。
- **图片在请求里的位置**：
  - 用户上传：用户消息里依次是 `<image name=[Image #N] path="…">`、图片、`</image>` 三段。
  - 工具查看和生成：Codex 的工具都经 `exec`（代码模式）调用，图片在 `custom_tool_call_output` 的输出里。查看的文件路径写在调用代码里；生成的图后面跟着一段说明保存路径的文字。
  - 托管生图的结果（`image_generation_call.result`）是必填字段，换不成文字。
- **条目编号**：请求里的消息和工具输出，带着和本地记录完全相同的 `id`，以及所在轮次的 `turn_id`。所以本地记录和请求能按条目对上，不受历史压缩和位置变化的影响。
- **改图取图**：改图工具从 Codex 本地的历史取最近的图，不看代理发出的内容，所以取消勾选不影响改图。
- **压缩**：远程压缩（v2）走同一个 `/responses` 接口，同样会被改写。
- **请求体**：zstd 压缩的 JSON。实测 `JSON.parse` 再 `JSON.stringify` 能逐字节还原。

### 设计

- **编号**：从任务的本地记录（rollout，只读）里按顺序找出所有图片出现记录，依次编号 IMG-001、IMG-002……
  - 编号只由记录内容决定，命令行（以后是面板）和代理各自读取，结果一致。
  - 记录只会追加，所以已有的编号不变。代理按文件增量读取，只解析新增的行。
  - 分叉任务的前半段历史在父任务的记录文件里，要沿 `history_base` 跨任务读取。
  - 工具查看的图，如果路径是经变量传进去的，就取不到文件名；这时借用内容相同、有名字的那一张的名字。
- **识别键**：条目 `id` 加图片在条目里的序号；没有 `id` 时用 `call_id`；两者都没有时，用类型、轮次和内容哈希。
- **内容相同**：先比较 base64 内容的哈希，再比较 PNG 解码后的像素哈希。
- **勾选状态**：每个任务一个文件，只记被取消的识别键。验证阶段放在 `local/selection/`；产品里放在工具自己的数据目录，不写进 `~/.codex`。
- **改写**：只处理有取消项的任务的 `/responses` 请求。步骤是解压、解析、替换、重新压缩，然后转发。
  - 替换规则见 spec 的“占位符”。
  - 用户上传的图，连同前后两段路径标签，一起换成一段文字。
  - 没有需要替换的图时，原样转发原始字节。
- **切换到 HTTP**：
  - 任务一有取消项，代理就对它的 WebSocket 握手回 426；
  - 它已有的 WebSocket 连接，空闲 1.5 秒后由代理关掉；
  - 从下一次请求起，这个任务在当前会话里一直走 HTTP；
  - 没有取消项的任务照常走 WebSocket。
- **原样放行**：下面几种情况原样转发，并记下原因：
  - 请求解不开，或者解析失败；
  - 含有 JavaScript 表示不了的大整数；
  - 找不到本地记录；
  - 改写出错。

  托管生图的结果无法替换，所以命令行不允许取消它。
- **日志**：只记编号、类型、占位符种类、大小，以及图片内容哈希的前 16 位。不记文件名，不记对话内容。
- **调试抓包**：`--dump-requests` 把请求存进 `local/`，图片只留哈希和长度。只用于合成的测试任务。

### 验证顺序

1. P2-1 抓包：用合成图片覆盖上传、工具查看、生成三种来源，确认上面的请求结构。
2. P2-2 到 P2-4：识别、编号、改写，并接入代理，配单元测试。
3. P2-5 自测：用我们自己启动的 app-server，环境和桌面版一致（去掉 `NO_PROXY`、打开 `respect_system_proxy`、地址用 `localhost`）。在同一个任务里依次上传、取消、询问、重新勾选、再询问、全部勾选。
4. P2-6 桌面版验证【需用户】。

### 已知限制

- 取消勾选时，如果这个任务正在一轮对话中间，而且还在用 WebSocket，这一轮剩下的请求可能仍带着原图。从下一轮起一定生效。
- 生图和改图：当前版本要靠 `.env` 里的 `NO_PROXY` 才能经过代理，见第 9 节“不等更新的办法”。
- 桌面版会在用户消息里附一段 “Files mentioned by the user”，写着上传文件的完整路径。代理不改这段用户消息的文字，靠占位符里“不要自己用工具去读取”的要求约束模型；P2-6 里模型遵守了。

## 11. 面板（P3）

### 已查证的事实

依据桌面版自带的 `0.155.0-alpha.16.4` 的源码、上游 issue 和本机检查：

- **对话里的界面（MCP Apps）**：
  - 工具在自己的说明里用 `_meta.ui.resourceUri` 指向一个 `ui://` 页面；模型调用这个工具时，桌面版在对话里显示这个页面。
  - `_meta["openai/ui"].preferredModelDisplayMode` 可以选 `inline`（嵌在对话里）或 `fullscreen`（全屏）。
  - 页面的类型是 `text/html;profile=mcp-app`，在沙箱里运行，通过 postMessage 和桌面版握手，再经桌面版回调同一个服务的工具。
  - 界面信息会存进聊天记录，重启后不用重新查询插件也能显示出来。
- **已知问题（上游未修）**：
  - [#47512](https://github.com/openai/codex/issues/47512)：Windows 上页面偶尔整块空白，都出现在页面地址变化之后。所以页面地址要保持固定。
  - [#45913](https://github.com/openai/codex/issues/45913)：页面访问不了 `http://localhost`，即使列进了 CSP。所以面板只经桌面版回调插件服务拿数据，缩略图用 data URL。
- **插件格式**：`.codex-plugin/plugin.json` 可以带技能（skills）、MCP 服务（`mcpServers`）和钩子（hooks）。钩子事件有 `SessionStart`、`UserPromptSubmit` 等，可以执行命令。
- **接入配置**：`config.toml` 的 `[mcp_servers.<名字>]` 写启动命令；`default_tools_approval_mode = "approve"` 让它的工具不用逐次确认。
- **桌面版的程序**：OpenAI.Codex 安装目录下的 `ChatGPT.exe`，窗口标题是“ChatGPT”。截屏脚本 `spike/scripts/capture-codex.ps1` 按安装目录找这个窗口，只截它。

### P3-1 实测结果（2026-09-24，桌面版 26.917）

- 面板能用：出现在 Codex 右侧的侧栏里，带标签页。静态页面、data URL 小图、和桌面版的握手、回调插件服务，全都成功。
- 页面访问 `localhost` 被 CSP 拦截，和 #45913 一致。
- 桌面版两套接口都提供：MCP Apps 的 `ui/*` 消息，以及 Apps SDK 的 `window.openai`（有 `callTool`、`setWidgetState`、`requestDisplayMode` 等）。
- 工具结果会原样送到页面；面板回调工具时，桌面版会在 `_meta` 里带上当前任务的 `threadId`，所以面板天然知道自己属于哪个任务。
- 插件服务是按会话启动的：桌面版启动时拉起了 6 个实例，其中 5 个很快被结束，当前任务那一个一直在运行，面板的回调也由它处理。
- 插件服务的工具不会直接列给模型，要在代码模式里搜索才能找到；gpt-6-sol 第一次没找到，点名工具后才打开。每次打开还要花一轮请求。所以面板不能靠模型来打开。
- 自己加的钩子默认是“未信任”，要用户在 Codex 界面里批准一次才会执行；插件服务则由 Codex 直接启动，不用批准。

### 设计

先把核心做完、测稳，再做界面（用户 2026-09-24 决定）。

- **引擎**：就是代理进程，全机只运行一个（占用端口即表示已在运行）。
  - 负责改写请求，并把每个任务最近一次请求的统计写进状态文件：大小、哪些图发了、哪些图被替换。
  - 定时检查 Codex 进程，Codex 全部退出后自己退出。
- **插件服务**：由 Codex 启动。
  - 启动时确保引擎在运行，之后每隔几秒再检查一次；引擎崩了会自动拉起。
  - 同时给面板提供数据：图片列表、缩略图、勾选和取消、发送预览、模型索要的编号。
  - 它和引擎之间只通过文件共享状态，任何一方不在，另一方都照常工作。
- **不用钩子**：插件服务本来就由 Codex 启动，不用用户批准，比钩子更适合做启动器。
- **安装和恢复**：一个命令写好全部带标记的配置（代理地址、`respect_system_proxy`、插件服务，需要时加 `.env`），一个命令全部恢复。
- **界面**：见第 12 节。做成右侧侧边面板里的 MCP App，用户从“新建标签页 → 插件和 MCP”手动打开（P4 已完成）。

### 验证顺序

1. P3-1 试验面板（已完成，结果见上）。
2. P3-2 引擎：全机单实例、确保运行（ensure）、Codex 退出后自动退出、记录每个任务最近一次请求的统计。
   - 实测（P3-5）：Codex 会把插件服务和它拉起的进程一起管理，引擎随拉起它的那个插件服务实例一起结束；其他实例的看门狗（每 3 秒）会重新拉起，所以最多断开 3 秒。这也让“随 Codex 退出”自动成立。要彻底避免断开，可以改用 Windows 计划任务启动引擎，但需要用户同意在系统里注册任务，暂不做。
3. P3-3 插件服务：启动器和看门狗，加上面板的数据工具。
4. P3-4 安装和恢复命令。
5. P3-5 稳定性自测：多个任务同时用、历史压缩、引擎中途重启、Codex 退出后引擎自动退出、分叉任务。
6. P4 界面，做到关键节点截图给用户看；P5 打包成插件、写说明。

## 12. 面板（P4）

### 已查证的事实

依据桌面版 26.917 的前端代码，以及 P4 实测：

- **不经过模型的入口**：工具可以在 `_meta["openai/ui"].entrypoints` 里声明入口，工具同时要用 `_meta.ui.resourceUri` 指向一个 `ui://` 页面。入口有四种：
  - `thread`：出现在任务右侧侧边面板的“新建标签页 → 插件和 MCP”里；
  - `global`：出现在左侧导航栏；
  - `settings`：出现在设置里；
  - `file`：按扩展名打开文件。
  - 列表里显示的名字是工具的 `title`，图标取自插件服务 `serverInfo.icons`，只收 https 或 data URL，可以分浅色和深色。
- **打开后**：
  - 桌面版先读页面资源，再用当前任务的编号调用这个工具，把结果交给页面。页面之后的工具调用也带着这个任务的编号（`_meta.threadId`）。
  - 这些调用不写进聊天记录，不占模型的上下文（P4 实测：任务记录里没有一条面板调用）。
  - 工具结果的 `_meta` 会原样交给页面，所以图片数据放在 `_meta` 里。
- **主题**：握手时，桌面版会传来主题（light/dark）和一组样式变量，包括颜色和字体，例如 `--color-background-primary`、`--color-text-primary`、`--font-sans`。页面用这些变量，就和 Codex 的外观一致。
- **标题栏**：没有给插件的入口。

### 设计

- **入口工具**：`cam_panel`，标题“上下文素材”，声明 `thread` 入口，页面固定为 `ui://codex-attachment-manager/panel.html`（地址变了可能白屏，见 #47512）。它和其他面板工具一样只给面板用（`visibility: ["app"]`）。
- **页面**：`spike/src/panel.html`，单文件，不联网。
  - 按轮次列出任务历史里的图；缩略图排队加载，看得见的优先；点开后预览大图。
  - 勾选先暂存，点“确定”才调用 `cam_set_selection` 保存。
  - 每 3 秒刷新一次，没有变化就不重画。页面报告自己不可见时降到 15 秒一次，因为有的宿主会误报。
- **取图**：`cam_image`。PNG 超过要求的尺寸就缩小，其他格式原样交给页面，由浏览器缩放。
- **开发页**：`spike/scripts/panel-dev.ts` 在浏览器里扮演 Codex 的侧边面板，用合成测试图调通页面，不用重启 Codex。页面上的“切换明暗”“加一张图”只用来模拟 Codex 的操作，不会出现在 Codex 里。

## 13. 打包成插件（P5）

### 已查证的事实

依据桌面版 26.917、它自带的命令行 0.155，以及它自带的插件：

- **插件**：插件目录里放 `.codex-plugin/plugin.json`。
  - 字段有 name、version、description、author、homepage、repository、keywords；`mcpServers` 指向 `.mcp.json`。
  - `interface` 里有 displayName、shortDescription、longDescription、developerName、category、capabilities、brandColor、logo、composerIcon。
- **`.mcp.json`**：
  - 服务的 command、args、cwd（`.` 表示插件目录）、default_tools_approval_mode、startup_timeout_sec；
  - `env_vars` 是一张白名单，列出允许传给服务的环境变量。
- **插件市场**：一个目录里的 `.agents/plugins/marketplace.json`，列出其中的插件和它们的相对路径。
- **命令行**：
  - `codex plugin marketplace add <本地路径、owner/repo 或 Git 地址>`、`codex plugin add <插件>@<市场>`、`codex plugin remove`、`codex plugin marketplace remove`；
  - 安装会把插件目录复制到 `~/.codex/plugins/cache/<市场>/<插件>/<版本>/`，并在 config.toml 里写 `[marketplaces.<市场>]` 和 `[plugins."<插件>@<市场>"]`。
- **桌面版自带的东西**：
  - 命令行在 `%LOCALAPPDATA%\OpenAI\Codex\bin\<版本号>\codex.exe`；
  - 自带 Node 24，能直接运行 TypeScript。自带插件用一个 .cmd 启动脚本按顺序找这个 Node。
- **重启才生效**：正在运行的桌面版不会立即加载新装的插件。

### 设计

- **目录**：
  - `plugin/` 是插件本体：清单、`.mcp.json`、`scripts/launch.cmd`、`src/`；
  - 仓库根目录的 `.agents/plugins/marketplace.json` 指向它；
  - `spike/` 留测试和实验脚本。
- **启动**：
  - `.mcp.json` 用 `cmd.exe /d /s /c call ./scripts/launch.cmd ./src/plugin-server.ts` 启动插件服务，`launch.cmd` 优先用 Codex 自带的 Node（v0.1 起改成三个平台通用的 `./scripts/launch`，见第 14 节）；
  - 根目录的 `cam.cmd` 用同一个脚本运行命令行，用户不用另装 Node。
- **数据目录**：`%LOCALAPPDATA%\codex-attachment-manager`。插件目录会在更新时被 Codex 替换，而且不往 `~/.codex` 里写。
- **安装顺序**：
  1. 检查和用户自己设置的冲突，然后备份 config.toml；
  2. 登记市场，装插件（每次都重装，让 Codex 的副本和仓库一致）；
  3. 自检装好的副本：用它自己的启动脚本起服务，问工具列表和面板页面；
  4. 写代理设置；
  5. 迁移旧的勾选记录，确保引擎在运行。
- **卸载顺序**：先去掉代理设置，恢复直连；再卸插件、去掉市场。
- **已知风险**：只在插件页面关掉插件、不运行 uninstall，Codex 会连不上，见 spec.md 第 5 节。

## 14. 发布准备（v0.1）

### 已查证的事实

依据 Codex 的公开源码（codex-rs）、官方文档、桌面版 26.917 的前端代码，以及 CI 上 npm 版命令行 0.157.0 的实测：

- **三个平台都有桌面版**：Linux 版 2026-08 起预览，包名 `chatgpt`。macOS 桌面版的命令行在 `<app>/Contents/Resources/codex`；Codex 自己的安装脚本把命令行放在 `~/.local/bin/codex`。桌面版会把 `CODEX_CLI_PATH`、`CODEX_ELECTRON_RESOURCES_PATH` 传给插件服务。
- **插件服务怎么启动**：
  - Windows 上用 `which` 按 PATHEXT 解析命令，所以 `./scripts/launch` 会找到 `launch.cmd`；
  - macOS、Linux 上直接运行命令，并放进新的进程组；
  - 插件的 `cwd` 按插件目录解析。OpenAI 自带插件也是同一套：一个无扩展名的 POSIX 脚本，加一个同名的 `.cmd`。
- **Windows 的 Job**：插件服务在一个“关闭即结束、不许脱离”的 Job 里，它启动的引擎也在里面，服务一结束引擎就跟着结束。所以插件被移除后，Windows 上没有我们的进程还能收尾。macOS、Linux 上引擎用 `setsid` 脱离了进程组，会留下来。
- **桌面版的插件页面能添加插件市场**：来源可以是 GitHub 仓库（`owner/repo`）、Git 地址或本地文件夹，可选 Git ref。所以用户可以完全不开终端：添加市场、装插件，再在面板里启用。
- **Windows PowerShell 5.1**：`irm … | iex` 把 GitHub 发布文件按 Latin-1 解码，脚本里的中文会乱码，所以两个 `.ps1` 只用 ASCII。
- **Windows 上的句柄继承**：Node 在 Windows 上启动子进程时，子进程会继承父进程可继承的句柄。所以引擎会拿着启动它的脚本的输出管道；只有测试会因此多等，用户不受影响。

### 设计

- **一份 `.mcp.json` 通用三个平台**：命令写 `./scripts/launch`，`scripts/launch`（POSIX，可执行位，LF）和 `scripts/launch.cmd` 按同样的顺序找 Node：
  1. Codex 传来的路径；
  2. 桌面版资源目录里的 `cua_node`；
  3. primary runtime；
  4. PATH 上 24 以上的 `node`。
- **平台差异**：
  - 进程检测：Windows 用 `tasklist`，其他平台用 `ps` 按可执行文件名 `codex` 统计；
  - 系统代理：Windows 读注册表，macOS 读 `scutil --proxy`（只认 HTTP(S) 代理），Linux 只看环境变量；
  - 数据目录：macOS 在 `~/Library/Application Support`，Linux 按 XDG。
- **升级时替换引擎**：引擎报告 build（运行目录里 .ts 文件的哈希，换行统一成 LF）和版本。插件服务发现代码不同、版本不低，就请旧引擎退役：
  - 旧引擎立刻停止监听，放掉空闲连接，把正在进行的请求和 WebSocket 这一轮做完再退出；
  - 新引擎马上接手端口。
- **启用、停用**（`setup.ts`，命令行、面板和引擎共用）：只增删带标记的块，改之前备份 config.toml，整文件写好再替换。
  - 面板的 `cam_setup` 只接受面板的调用；
  - 启用、停用都要重启 Codex 才生效，面板会提示。
- **插件被移除或关掉、没先停用**：
  - 引擎每 15 秒检查一次，判断依据只用明确的迹象：插件缓存目录不在了，或者 config.toml 写着 `enabled = false`；
  - 连续两次，或者引擎退出前再查一次，就恢复直连；
  - 在 Windows 上这一步通常来不及（见上面的 Job），所以面板、插件说明和 README 都写“先停用再移除”，卸载命令负责恢复。
- **安装路径**：
  - 插件页面：添加市场 `chipfighter/codex-attachment-manager` → 装插件 → 面板里启用 → 重启；
  - 一行命令：`install.ps1` / `install.sh` 用 Codex 的命令行装插件，再运行装好的副本里的 `cam.ts setup`；
  - 卸载：`uninstall.ps1` / `uninstall.sh` 不需要 Node 和插件文件，先按同样的规则去掉带标记的块，再卸插件和市场。
- **发布**：推送 `v<版本>` 标签后，Release 工作流先在三个平台跑 CI，再核对标签和插件版本一致，然后把标签写进四个脚本，建一个草稿 Release。说明取自 CHANGELOG.md。人工看过再发布。
  - 三个平台共用同一个插件，只有安装脚本分平台；
  - `releases/latest/download/<脚本>` 始终指向最新的发布。
- **验证**：
  - `spike/src/plugin-smoke.ts`：Codex 自己的命令行装插件，app-server 开任务，插件服务就绪，引擎启动；
  - `spike/src/scripts-smoke.ts`：真的跑安装、卸载脚本，config.toml 和 .env 恢复原样；
  - CI 在 Windows、macOS、Linux 上都跑这两项和全部单元测试。

## 15. 面板和任务的对应（v0.1-9 到 v0.1-11）

### 已查证的事实

依据桌面版 26.917 的前端代码、Codex 的公开源码（codex-rs）和用户 2026-09-25 的实测：

- **侧边面板按任务保存**：每个任务各记自己的面板开没开、有哪些标签页、哪个在前面。切到没开过面板的任务，面板是关的；切回来，原来的标签页还在。一个任务可以开好几个标签页。
- **面板里的调用带着固定的任务编号**：面板每次调用插件，带的都是它被打开时所在任务的编号，之后不会变。
- **新任务页面**：在这里打开的面板，绑在 Codex 预先准备的任务上。发第一条消息时，Codex 可能丢掉这个预备任务、另开一个，并把标签页带到新任务上，但面板里的编号不变（v0.1-8）。
- **分叉**：Codex 分叉时会把原任务的侧边面板布局复制过去。用户实测：在分叉里新开的面板绑在分叉上，勾选按第 1 节的规则继承。
- **任务名**：在 `<CODEX_HOME>/session_index.jsonl` 里，每行 `{id, thread_name, updated_at}`。名称只追加，同一个任务以最后一行为准；Codex 删除某个任务的名称时，会整个文件重写。
- **任务来源**：任务记录的第一行（`session_meta`）写明：
  - `source`：`cli`、`vscode`、`exec`、`mcp`，或者 `{subagent: …}`、`{internal: …}`；
  - `thread_source`：`user`、`subagent`，或者某个功能的名字；
  - `forked_from_id`、`parent_thread_id`。
  - 带历史启动的子代理，Codex 也记成从父任务分叉（`forked_from_id` 是父任务）。
- **每个任务各有一个插件服务进程**。所以分叉出来的任务第一次开面板时，插件服务是新起的，内存里的缓存是空的。
- **任务记录的存放**：放在 `sessions/YYYY/MM/DD`，按任务创建那天的本地日期分目录。新任务、分叉和长任务的后续分页，都落在当天的目录里。
- **记录第一行的时间**：每行开头的 `timestamp` 是写入这一行的时间。新任务的记录是发第一条消息时才写的，所以第一行的时间就是任务开始的时间。
- **归档的任务**：用户归档任务后，Codex 把它的记录挪到 `<CODEX_HOME>/archived_sessions`。从它分叉出来的任务，记录开头仍然指向它的某一段历史（`history_base`）。用户 2026-09-25 实测：原任务归档后，分叉出来的任务打开面板报“rollout segment not found”（v0.1-12）。
- **压缩的旧记录**：新版 Codex 会把一周没动过的任务记录压缩成 `.jsonl.zst`。要往里追加时，先解压回 `.jsonl`、再删掉压缩文件。以前的代码只认 `.jsonl`，面板打开这种旧任务时是空的。

### 设计

- **标题**：显示 `session_index.jsonl` 里的名称；没有名称时，显示第一条用户消息的开头；任务还没开始时，显示“新任务”。改名后，面板下次刷新时跟着变。
- **新任务自动绑定**：
  - 面板页面记下自己哪些时间段显示在屏幕上（页面可见、宽高不为 0），每次读数据时带给插件服务：
    - 第一段从页面打开前 10 秒算起，因为发第一条消息时 Codex 可能重新加载面板页面；
    - 页面被挡住或切走后再显示，就开始新的一段；最多保留 20 段。
  - 面板所在的任务还没有记录时，插件服务列出符合条件的任务：
    - 开始的时间落在某一段里，或者在这一段结束后 5 秒内（用户发完消息马上切走，页面还没来得及记下）；
    - 来源不是子代理、内部任务、`exec` 或 `mcp`，不是分叉，`thread_source` 为空或者是 `user`。
  - 正好一个就自动切过去；两个以上就列出名称，让用户选。
  - 为什么按时间段，不按“最近 30 秒”：第一版按 30 秒算。可是用户发完第一条消息就切到别的窗口、过一会儿才回来，任务就超过 30 秒了，面板会一直等下去。按时间段算，回来多晚都能切过去；在别的页面开始的任务，因为当时这个面板不在屏幕上，照样不会被认走。
  - 已知的例外：两个窗口并排、两个面板都开在新任务页上，在一个窗口里发消息，两个面板都会切过去。
  - 绑定记在数据目录的 `bindings/<面板的任务编号>.json`。之后这个标签页的所有调用都按新任务处理，面板重新加载后也一样。
  - 只接受面板的绑定调用，模型调用会被拒绝。
- **卡顿**：
  - 实测（合成数据：12 张 1920×1080 截图共 10.6 MB，另有 400 个其他任务）：
    - 新进程第一次读面板数据要 1.2 秒，其中 0.9 秒花在逐张解码 PNG、计算像素指纹；
    - 每张缩略图要 0.14 秒；
    - 之后每次读面板数据要 30–60 毫秒，主要花在遍历所有任务记录的目录上。任务越多越慢。
  - 改法：
    - 像素指纹存进数据目录的 `cache/pixels/`，引擎和各个插件服务共用。只存指纹，不存图片内容。
    - 任务记录的目录只完整遍历一次，之后每次只重新列出今天和昨天的目录；每分钟再完整遍历一次，作为兜底。
  - 缩略图不写到磁盘，免得在数据目录里留下图片内容；仍然在内存里缓存。
  - 改后实测（同样的数据）：
    - 分叉的任务在新进程里第一次读面板数据：0.07 秒（指纹已由引擎或原任务的面板存好）；
    - 之后每次读：2–6 毫秒；
    - 每张缩略图 0.08 秒，一张张补上，不挡列表。
- **压缩的旧记录**：`.jsonl.zst` 用 Node 自带的 zstd 解压后整份读入；同时存在 `.jsonl` 时以它为准。
- **归档的任务**：完整查找时把 `archived_sessions` 也算上，同一段记录两边都有时以 `sessions` 里的为准。读的时候找不到某一段（例如上次查找之后才归档），立刻重新查找一遍，最多每 5 秒一次。
- **找不到的历史**（v0.1-13，用户 2026-09-25 要求）：重新查找之后，前面某一段历史还是找不到（例如原任务的记录被删掉了，不是归档），就跳过这一段，照常读剩下的：
  - 面板列出剩下的图，并提示“前面有一段历史找不到了，那一段里的图片没法列出”；
  - 编号和轮次从剩下的部分重新算；
  - 引擎也按剩下的部分改写。取消过的图照样换成占位符，认不出的图原样发送。
  - 任务自己的最后一段找不到时，仍然当作没有记录。

## 16. 中英文界面（v0.1-14）

### 已查证的事实

- **Codex 把界面语言告诉面板**：MCP 应用规范里，Codex 打开面板时给的 host context 带 `locale`，变了会再发一次。Codex 实际给不给，重装后用 `cam status` 确认（显示语言来自 Codex 还是系统）。
- **插件清单只能写一种文字**：Codex 的插件清单（codex-rs 的 manifest.rs）里，名称、简介、详细说明都是普通字符串，没有按语言切换的写法。
- **工具列表在插件服务启动时读取**：标签页标题就是面板工具的 `title`，所以它的语言在插件服务启动时就定了。

### 设计

- **判断语言**（`language.ts`）：以 `zh` 开头的都算简体中文，其他都算英文。
  - 面板：先看 host context 的 `locale`，没有就看浏览器语言。
  - 面板每次调用都带上语言；读面板数据时还带上“来自 Codex 还是系统”，插件记在数据目录的 `language.json` 里，变了才写。
  - 引擎（发给模型的文字）和工具列表（标签页标题）读这份记录；没有记录时用系统语言。
  - 命令行一律按系统语言：POSIX 的 `LC_ALL`、`LC_MESSAGES`、`LANG`，都没有就看运行时报告的语言。
- **文字表**：
  - 插件服务和命令行的文字在 `messages.ts`；
  - 面板的文字在 `panel.html` 里一段 JSON，英文可以多一条 `key_one`（数量为 1 时用）；
  - 发给模型的文字在 `rewrite.ts`，中文原样保留，改动前后逐字节比对过。
  - 单元测试检查两种语言的条目一一对应、占位的 `{名字}` 也一致。
- **插件服务返回的文字**：报错和结果按面板带来的语言给出；改写失败的原因改成代码，由面板翻译；和用户设置冲突的报错带一个文字键，面板和命令行各按自己的语言显示。
- **面板认模型索要**：英文说明让模型回复“need IMG-004”，面板也认带引号的写法。
- **测试**：环境变量 `CAM_LANG=zh|en` 可以固定语言（测试、开发用）。断言中文措辞的测试都固定成中文：第一次推到 CI 时，这些测试在英文系统上全部失败，而且在本机也会随记下的语言变化。
- **已知代价**：同一个任务中途切换 Codex 的语言，说明文字会变，模型那边缓存的上下文要重算一次。
- **验证**：`v01-placeholder-selftest.ts --lang en` 用同样的五轮对话检查英文说明：模型不收回之前的回答，被问到没说过的细节时回复“need IMG-xxx”。
