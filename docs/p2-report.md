# 代理验证 P2 报告：按勾选改写

> 2026-09-24，由 Claude 执行。本报告只写统计和测试任务里的简短问答，不含真实对话、图片和本机路径。设计见 [plan.md](plan.md) 第 10 节，任务见 [tasks.md](tasks.md)。

## 1. 结论

自测（P2-5）和桌面版验证（P2-6，第 5 节）都通过：在同一个任务里取消图片、重新勾选，都从下一次请求起生效，对话不中断。桌面版的生图和改图也经过了代理。

自测用我们自己启动的 app-server。它和桌面版用的是同一个 `codex.exe`，环境也一样：去掉 `NO_PROXY`，打开 `respect_system_proxy`，地址用 `localhost`，不改 `config.toml`。测试图片都是合成的：

- `a.png`：白底红方块，右下角有一个黑色小方块；
- `b.png`：黄底蓝圆，左上角有一个绿色小方块；
- `b-copy.png`：`b.png` 改名后的副本，字节完全相同；
- `noise.png`：约 3 MB 的噪点图，用来看能省下多少字节。

| spec 第 4 节 P2 验收项 | 结果 |
|---|---|
| 1. 取消的图不再发送，请求变小 | 通过：a.png、b-copy.png、noise.png 的内容都没有出现在请求里（按内容哈希核对）。请求从 3,205,210 字节降到 37,382 字节（压缩后），解压后是 4,312,287 → 105,242 字节 |
| 2. 占位符种类正确 | 通过：a.png、noise.png 是普通占位符；b-copy.png 是指向 b.png（IMG-002）的重复占位符 |
| 3. 模型不编造，并按约定索要 | 通过（调整措辞之后，见第 4 节）：模型回答“需要 IMG-001，才能回答。”；对 b-copy.png 则按 IMG-002 正确说出“黄色背景……蓝色圆形，左上角有一个绿色小方块” |
| 4. 重新勾选后能正确使用 | 通过：模型回答“白色背景，主要形状是红色正方形，右下角有一个黑色小方块标记。” |
| 5. 同一个任务，不报错、不重连 | 通过：4 轮都在同一个任务里，没有报错和重试 |
| 6. 全部勾选时原样转发 | 通过：最后一轮没有改写，请求带着全部 4 张图 |
| 7. 原始记录只读 | 通过：代码只读取本地记录，勾选状态存在 `local/selection/` |

## 2. 过程中确认的事

- **切换到 HTTP 很顺畅**：第一轮走 WebSocket。取消勾选后，代理在连接空闲时把它关掉；第二轮 Codex 重新握手，收到 426，改走 HTTP，之后一直走 HTTP，没有任何报错或重试。
- **本地记录和请求能按条目对上**：请求里的每条消息和工具输出，都带着和本地记录相同的 `id`，所以代理能准确认出每张图是哪一次出现的，改名的副本也能按内容认出来。
- **重新序列化没有副作用**：真实请求体经 `JSON.parse` 再 `JSON.stringify` 能逐字节还原，改写只改变被替换的部分。
- **小图不一定省字节**：只取消几 KB 的小图时，占位符文字可能比图还大，压缩后的请求甚至略大一点（第一次自测：37,037 → 37,140 字节）。省字节主要靠大图，这符合预期。

## 3. 耗时（真实样本实测）

用阶段 0 的真实样本测（只读）。原任务一共 14 次图片出现，其中 10 张内容不同，完整请求解压后 43.9 MB、压缩后 32.7 MB。

| 步骤 | 耗时 |
|---|---|
| 字节指纹（SHA-256），每张大图 | 1–5 毫秒；14 张合计 48 毫秒 |
| 像素指纹（解码 PNG），每张大图 | 40–110 毫秒 |
| 第一次建立任务索引（含全部指纹） | 约 1.2 秒；每个任务只算一次 |
| 之后再读索引（记录没变） | 约 8 毫秒 |
| 代理改写一次完整请求（43.9 MB） | 约 0.6 秒；其中解压 0.09、解析 0.09、找图 0.05、替换不到 0.001、序列化 0.21、压缩 0.12 秒 |

- 对照：Codex 自己压缩同一个请求约 0.18 秒。
- 没有取消项的任务，代理原样转发，不做这些处理。
- 这两个样本里，字节指纹已经找出全部重复，像素指纹没有找出新的。
- 测量中发现并修好了一个问题：分叉任务的前半段历史在父任务的记录文件里，原来读不到；现在沿 `history_base` 跨任务读取，并加了单元测试。

## 4. 占位符措辞的调整

- **第一次自测**：原措辞是“需要查看时，请在回复里写‘需要 IMG-001’”。问题里带着“看不到的就直说”这句话时，模型只回答“看不到，无法判断”，没有索要。
- **调整**：措辞改成“如果回答需要看这张图，请在回复里写出‘需要 IMG-001’，用户可以在下一轮重新勾选提供”，问题里也去掉了那句引导。
- **第二次自测**：模型按约定索要了。用户 2026-09-24 认可现在的措辞。

## 5. 桌面版验证（P2-6）

用户在 Windows 桌面版（自带 `0.155.0-alpha.16.4`）里新建一个测试任务，上传了 `b-copy.png`、`a.png`、`b.png`（依次编号 IMG-001、IMG-002、IMG-003），勾选由 Claude 用命令行操作。工具这次写入了 `config.toml` 的两段设置和 `.env` 里的 `NO_PROXY`。

| 步骤 | 结果 |
|---|---|
| 第 1 轮：上传三张图 | 经过代理，走的是 WebSocket |
| 取消 IMG-001（副本）和 IMG-002 | 代理关掉了这个任务空闲的 WebSocket 连接 |
| 第 2 轮：问 a.png 和 b-copy.png | 握手收到 426，改走 HTTP；请求被改写：IMG-001 换成指向 IMG-003 的重复占位符（这次是靠前的副本指向后面的原图），IMG-002 换成普通占位符，只发出 1 张图。模型回答：“需要 IMG-002。IMG-001 与 b.png（IMG-003）内容相同；我能看到的 b.png 是黄色背景、中央蓝色圆形，左上角有绿色小方块。” |
| 重新勾选 IMG-002，第 3 轮再问 | 模型回答：“白色背景，中央是红色方块；右下角有一个黑色小方块。” |
| 第 4 轮生图、第 5 轮改图 | `images/generations` 和 `images/edits` 都经过代理，都返回 200。不用等上游 #47742，P1-4 剩下的问题也一并解决 |
| 全程 | 同一个任务，没有报错和重试 |
| 恢复配置 | 两处标记段落都已删除，`.env` 只剩我们那一段，所以整个文件删除。`config.toml` 和打开之前相比，只多了桌面版自己写的两处：新的管道名、新任务文件夹的信任设置 |

两个新发现：

- **桌面版会在用户消息里附一段 “Files mentioned by the user”**，写着上传文件的完整路径。代理没有改这一段。这次模型遵守了占位符，没有自己去读文件。
- **生成的图没有进入对话历史，结果改错了图，界面上还多了空的图片框**：
  - 第 4 轮，模型在代码模式里按 `r.content` 读取生图结果，但这个结果的结构是 `{image_url, output_hint}`，本该用 `generatedImage(r)`。结果生成的图没有放进对话历史，工具附带的提示（“图片已经显示给用户，回复里不用再贴”）模型也没看到。
  - 于是模型在最后的回复里写了一个数据为空的 Markdown 图片 `![…](data:image/png;base64,)`，桌面版把它显示成一个灰色的空图片框，第 5 轮也一样。用户看到的真图，是生图工具自己显示的。
  - 第 5 轮，改图工具取“对话历史里最近的一张图”，取到的是第 1 轮上传的 `b.png`，把它左上角的绿色小方块改成了紫色，而没有去改生成的那张图。
  - **与代理无关**：同样错误的写法，在没经过代理的直连请求里也出现过 4 次，都用 gpt-6-luna，这次测试用的也是它。gpt-6-sol 和 gpt-5.6-luna 大多用 `generatedImage(r)`。用户当天直连的生图测试里，gpt-6-luna 第一次同样拿回了空结果，检查结果结构后，第三次才用对写法，前两次生成的图都白白浪费了。这是 Codex 代码模式和模型之间的问题，属于上游。

## 6. 待办和限制

- **生图和改图**：桌面版目前带的是 `0.155.0-alpha.16.4`，要靠 `.env` 里的 `NO_PROXY` 才能经过代理。上游从 `0.158.0-alpha.8` 起已修复，桌面版跟进后，就不再需要写 `.env`。
- **一轮中途取消**：如果这个任务还在用 WebSocket，这一轮剩下的请求可能仍带着原图，从下一轮起一定生效。
- **托管生图的结果**（`image_generation_call`）暂时不能取消。桌面版目前生图走 `exec` 工具，不受影响。
